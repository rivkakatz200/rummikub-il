# Rummikub bug fixes: recentActions[] highlight + dead-socket draw pending

Two bugs are fixed: the turquoise tile-highlight logic now tracks opponent moves since the local player's last completed turn (instead of toggling off during the local player's own turn), and the phantom "drawing…" placeholder tile that could get stuck in the rack is replaced by an `isDrawPending` state with an explicit 4-second timeout, server-side ERROR responses, an app-level PING heartbeat, and reconnect triggers. The approach is end-to-end: type changes in `rummikub.ts`, server logic in `server.ts`, client state in `App.tsx`, UI in `GameControls`/`PlayerRack`, and a new test script. Build, lint, and typecheck all pass.

Watch for: (1) **confirmed** — `highlightedTileIds` `useMemo` reads `myLastCompletedTurnNumberRef.current` as a snapshot; the ref is mutated before `setGameState` in the same handler, so the memo sees the correct updated value on the turn-boundary render — but the coupling is non-obvious and will silently break if the ref update is ever moved to a `useEffect`. (2) **confirmed** — `test:idle` uses `npx tsx` while every other script in `package.json` uses bare `tsx`; minor inconsistency but harmless. (3) **possible** — `lastReceivedAtRef` is initialized to `Date.now()` at component mount but the WebSocket may not have opened yet; if the first connection takes >45 s the dead-socket detector fires before any message is ever received.

**Verdict**: APPROVED

## High-level view

The monotonic `turnCounter` / `recentActions[]` pair replaces the old `roundNumber * 1000 + currentTurnIndex` formula. `recordAction` is a single bottleneck function that increments the counter and prepends to the array, so every action path (bot, human, timeout) passes through it. `getSanitizedGameState` adds `recentActions` to every broadcast so all clients receive the full recent history, not just their own perspective.

The client tracks each player's own last turn number in a ref (`myLastCompletedTurnNumberRef`) updated on every ROOM_STATE. The highlight `useMemo` reads the ref as a snapshot, which means on the exact render where both the ref and `gameState.recentActions` update together (i.e., the turn boundary), the evaluation order is ref-first then state — so the memo actually sees the updated ref on that same render. The interaction is correct but non-obvious: any future move of the ref update into a `useEffect` would silently break it.

The `isDrawPending` flow is set on send, cleared on ROOM_STATE or ERROR, with a 4 s fallback that triggers reconnect. The double-connect guard at the top of `connectWebSocket` prevents the visibility/online/dead-socket triggers from stacking sockets. The server PING setInterval is registered once at startup outside the per-connection handler, so it survives reconnects without accumulating.

The `room_not_found` ERROR path clears session storage and resets `gameState` and `myPlayerId`, preventing a stuck limbo lobby after the server restarts. The test script covers PING timing, out-of-turn DRAW_TILE, and nonexistent-room DRAW_TILE; PORT is read from `process.env.PORT`.

<summary>Issues (3)</summary>

1. **useMemo ref snapshot fragility** — `highlightedTileIds` reads `myLastCompletedTurnNumberRef.current` inline; the ref is mutated before `setGameState` so the current evaluation order is correct, but this is an implicit ordering dependency. Moving the ref update into a `useEffect` — a natural future refactor — would silently reintroduce an off-by-one. Convert to `useState` to make the dependency explicit in the memo's dependency array.

2. **test:idle uses npx tsx, others use bare tsx** — `"test:idle": "npx tsx scripts/testIdle.ts"` diverges from `"test:pool": "tsx scripts/testPool.ts"` and all other test scripts. Change to `tsx scripts/testIdle.ts` for consistency.

3. **Dead-socket timer starts before first WebSocket open** — `lastReceivedAtRef` is initialized to `Date.now()` at mount, but the WebSocket opens asynchronously. If the server is slow to accept (unlikely but possible in CI/cold-start scenarios), the 45 s detector fires before any message is received, triggering a spurious reconnect. Initialize the ref inside the `onopen` handler instead.

### useMemo dependency on a mutable ref

`highlightedTileIds` is a `useMemo` whose factory reads `myLastCompletedTurnNumberRef.current`:

```ts
const highlightedTileIds = useMemo(() => {
  if (!gameState?.recentActions?.length) return undefined;
  const myLastTurn = myLastCompletedTurnNumberRef.current; // snapshot of ref
  ...
}, [gameState?.recentActions, myPlayerId]);
```

The ref is mutated in the ROOM_STATE case *before* `setGameState(newState)` is called. React batches the state update, so the render that processes the state change also evaluates the memo — and at that point the ref already holds the new value. The behavior is correct today. The fragility is that the correctness depends entirely on mutation happening before the `setGameState` call, not on any React contract. Moving the ref update into a `useEffect` (which fires after render) would silently break the highlight on the turn boundary: the memo would see the stale ref value on the render where `recentActions` arrives, and only correct on the *next* render. A `useState` makes the dependency explicit and eliminates the ordering constraint.

### Test 2 ROOM_STATE race in testIdle.ts

Test 2 waits for a `ROOM_STATE` with `status: 'playing'` on `wsA`, then immediately reads `gameState.currentTurnIndex` to determine who is active. If the bot happens to go first and moves instantly (the server calls `handleBotTurn` synchronously on `START_GAME`), a second ROOM_STATE could arrive on `wsA` before the test reads `gameState`, advancing `currentTurnIndex`. The test would then send `DRAW_TILE` from the wrong player and get an ERROR on the *correct* player. The assert would still pass (ERROR is received), but the scenario tested isn't strictly "out of turn for a human player". This is a pre-existing limitation of single-snapshot game-state polling in tests, not a bug in the implementation.
